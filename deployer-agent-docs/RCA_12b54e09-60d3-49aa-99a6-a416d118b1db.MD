## Risk assessment — dedupeAllStores() (frontend/src/lib/store.js)
The cleanup keeps one row per key and then PUTs the cleaned snapshot to `/api/snapshot` as authoritative. For the collision groups above, the composite keys use JS `||` (first truthy wins):
- vendors key `vendorCode||tempRefId` → evaluates to `vendorCode` for all 3 AE0001 rows → a run would collapse them to 1, **dropping 2 distinct vendor records** (v_1792219493878, v_1792221931737).
- advance_requests key `refNo` → would collapse each of the 5 pairs to 1, **dropping 5 records** (ar_1791081047126, ar_1791081102782, ar_1791081135764, ar_1791081171852, ar_1791082132338 — or their 10-03 counterparts, whichever loses the keep-order).
- expenses keyed by refNo (if cleanup covers it) → would drop 5 extra EXR rows.
- payments key `pvNo` → would collapse the true `PV/HR/2026-09/2` duplicate to 1 (this one is desirable — it is a genuine dupe with identical id).

These are **prospective** losses if the cleanup runs and overwrites the server snapshot — not losses that have happened yet.
